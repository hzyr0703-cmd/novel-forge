# 作者真相与读者已知双时间线

> novel-forge 原创机制。灵感来自 oh-story 的双时间线设计，但本文件把操作规则补全，
> 并配套 `forge.py truth` 做机器校验。
>
> **解决的问题**：长篇最常见的两类吃书事故——
> ①角色提前知道尚未揭示的真相（读者觉得「他怎么知道的」出戏）
> ② 未揭示的真相被当成已揭示写出来（伏笔作废、逻辑崩坏）

## 一、核心原则

**作者知道的 ≠ 读者知道的 ≠ 角色知道的。**

这三个集合必须分开记。任何一条真相都必须同时回答：
- 作者侧知道什么（写作用）
- 读者侧知道什么（悬念保护）
- 角色侧知道什么（行为合理性）

大多数长篇崩盘的根因是后两者没分开。

## 二、文件结构

```
追踪/
├── _tracking-state.json          唯一权威，禁止手改
├── 上下文.md                     派生视图，只放下一章真正需要的
├── 伏笔.md                       派生视图
├── 逐章记录/                     派生视图
└── 时间线/
    ├── 作者真相.md                客观事实 + 读者认知 + 揭示状态
    └── 读者已知.md                只写读者已知的认知，不含真相
```

`作者真相.md` 表结构：

| ID | 首次登记章 | 故事时间 | 客观事实 | 读者当前认知 | 揭示状态 | 实际揭示章 |
|---|---|---|---|---|---|---|

`读者已知.md` 表结构：

| ID | 读者当前认知 | 认知截至章 |
|---|---|---|

两份文件的「读者当前认知」列**必须逐字一致**，`forge.py truth` 会校验。

## 三、登记规则

### 什么时候登记

**每个新真相首次出现时立刻登记**，不管它是否重要。包括：
- 反派的真实动机
- 主角能力的来源与代价
- 某个 NPC 的隐藏身份
- 已发生但读者还不知道的历史事件

**漏登记的代价**：写到第 50 章时已经忘了某条伏笔的揭示状态，读者记得你不记得。

### 三种揭示状态

| 状态 | 含义 | 角色可否据此行动 |
|---|---|---|
| **未揭示** | 作者知道，读者不知道 | ❌ 角色绝对不可知（除非他另有信息来源） |
| **候选** | 内容还没定，但有方向 | ❌ 不可写进正文 |
| **已揭示** | 读者已看到 | ✅ 可以 |

### 关键纪律

**未揭示真相的「读者当前认知」不能为空。**

写成「读者只知道有个讲了五十年没人听全过的故事」——这样后续任何情节都不会误泄底。

空着的行是bug 源头：`forge.py truth` 会直接拦截。

## 四、机器校验

```bash
python forge.py truth --book <书目录>
```

校验四条规则：

| # | 规则 | 级别 |
|---|---|---|
| 1 | 未揭示项的「读者当前认知」为空 | 阻断 |
| 2 | 未揭示项却填了实际揭示章（两列自相矛盾） | 阻断 |
| 3 | 未揭示的 E 编号却出现在读者已知表 | 阻断 |
| 4 | 未揭示项的读者认知里泄露了事实片段 | 提示 |
| 5 | 已揭示项在读者已知表无对应条目 | 提示 |

退出码非 0 即存在硬错误，必须修到通过。

## 五、典型事故与修法

### 事故 1：角色提前知情

```
原文：主角第一次见到商会会长，就说出了只有会长父亲才知道的旧事。
```

根因：写作者用了「作者真相」，没查「角色已知」。

修法：给主角补一个合法信息来源（他提前查过档案 / 有人告诉过他），
或改成他只是**试探**（用模糊话术看对方反应），而非直接说出。

### 事故 2：伏笔作废

```
第 5 章：老兵说「那封信我一直没寄出去」
第 40 章：（作者忘了这件事，直接让剧情推进）
```

根因：真相没登记进时间线，写到后面无从查证。

修法：第 5 章写入作者真相表，标「未揭示」，读者认知写「他知道有封信但没说寄给谁」。
第 38 章要回收时，`forge.py truth` 会提醒这条还挂着。

### 事故 3：认知与事实混淆

```
错误：把「客观事实」整段复制到「读者当前认知」
```

后果：后续任何用该表判断泄底的地方全部失效。

修法：读者认知写**读者能看到的部分**，不是真相全貌。

## 六、与伏笔追踪的关系

双时间线管「认知」，伏笔表管「悬念」。

| | 双时间线 | 伏笔表 |
|---|---|---|
| 记录什么 | 真相与认知的差| 未回收的悬念 |
| 粒度 | 一条事实 | 一处埋线 |
| 驱动 | `forge.py truth` | 上下文卡「活跃伏笔」段 |

一条伏笔回收时，两处都要更新：伏笔表划掉，同时双时间线里那条真相标「已揭示」并填实际揭示章。

## 七、落地建议

1. **第 1 章之前**就建好两份时间线文件，哪怕只有E001 一行。
2. 每章写完跑一次 `forge.py truth`，成本极低（读两个文件）。
3. 上下文卡里的「作者真相 / 读者已知」双段，是续写时的防剧透闸门——
   写正文前读这两段，就知道这一章哪些信息**不能**被角色使用。
