# recall-and-debt · 写前检索与债务压力

> 长篇崩盘的头号原因不是文笔差，是**忘了**。  
> 写到第 30 章忘了第 3 章埋的线，写到第 80 章忘了角色三年前的左撇子。  
> 本文档解决两件事：**动笔前捞回该想起的**，和**提醒你还欠读者哪几笔**。

---

## 一、为什么不用"让 AI 自己记住"

模型没有跨会话记忆。就算把 200 章正文全塞进上下文，也会有两个问题：

| 做法             | 问题                                |
| -------------- | --------------------------------- |
| 全文塞上下文         | 几十万 token 塞不下；塞下了也会在长上下文中段"注意力衰减" |
| 靠提示词提醒"不要忘记伏笔" | 模型没有索引，只能靠检索把事实**主动送到它眼前**        |

所以本方案不是"提醒模型记得"，而是**替模型查出来放在它面前**。  
这条思路与 webnovel-writer 的 RAG 一致，但实现刻意不同（见第六节）。

## 二、三个脚本，一条铁律

```bash
$S = ~/.workbuddy/skills/novel-forge/scripts

# 1) 重建检索索引（台账或正文有变动时）
python $S/recall.py --project <书稿根> index

# 2) 看本章该还哪几笔债
python $S/debt.py --project <书稿根> due --within 3

# 3) 按本章要素检索前文
python $S/recall.py --project <书稿根> query "老王 那封信 签名" --top 6
```

**铁律：<u>这两个脚本不产生任何真源状态。</u>**

- <u>真源永远只有 `_tracking-state.json`（由 `tracking_commit.py` 维护）</u>
- <u>`recall.py` 只写 `.recall-cache/`</u>，这是**可随时删除重建的缓存**
- `debt.py` 是**纯函数**，所有数字从台账实时算出台账一改结论立刻跟着变

如果哪天你发现"同一件事在两个文件里都有记录"，说明用法错了，不是脚本的功劳。

## 三、debt.py：债务压力模型

### 紧迫度怎么算

```
紧迫度 = 重要度权重 × (时间压力 + 停滞惩罚)
```

**时间压力**——按"距计划回收章的剩余章数"非线性上升：

| 剩余章数   | 系数                       | 含义                   |
| ------ | ------------------------ | -------------------- |
| > 30   | 0.05                     | 还早，读者不急              |
| 12– 30 | 0.20                     | —                    |
| 6 – 12 | 0.45                     | —                    |
| 3 – 6  | 0.75                     | 开始铺垫                 |
| 0 – 3  | 1.10                     | **临期，这章附近必接**        |
| 已逾期    | 1.40 + 1.60 × log₁₀(1 + 欠章数)  | 每多欠一章加罚 |

> **为什么逾期项不设硬上限**：早期版本封顶 2.40。600 章 / 50 条伏笔实测时，
> 所有债全部并列 2.40，排序彻底失效——50 条债看起来一样急，等于没有排序。
> 长篇里"欠得最久的那笔"必须永远排在最前面。改成对数增长后，同样 50 条债
> 分化成 11.81 / 10.39 / 9.92 / … / 7.38 的可读梯度：既拉开差距，
> 又不会让极端值压扁其他维度。

**停滞惩罚**——只看"埋了多久没动"，这是最容易被作者忘记的债：

| 已埋章数    | 系数   |
| ------- | ---- |
| < 5     | 0    |
| 5 – 12  | 0.20 |
| 12 – 25 | 0.50 |
| 25 – 40 | 0.85 |
| ≥ 40    | 0.85 + 0.90 × log₁₀(1 + (龄-40)/40) |

> 同样去掉了 1.20 的硬上限，理由一致：否则长龄债会集体并列。

**重要度权重**：极高 1.9 / 高 1.6 / 中高 1.35 / 中 1.0 / 中低 0.75 / 低 0.5

### 输出等级

| 等级   | 标记   | 处理方式                 |
| ---- | ---- | -------------------- |
| 高危   | `!!` | 紧迫度 ≥ 2.0，这章必接       |
| 逾期   | `!`  | 已超计划章数未回收            |
| 到期   | `!`  | 计划回收章 == 当前章         |
| 临期   | `*`  | 还剩 ≤ 3 章             |
| 无主悬念 | `?`  | **没设计划回收章**——不是债，是隐患 |
| 接近   | `-`  | 还剩 6 章内              |
| 宽松   | `.`  | 时间充裕                 |

> **「无主悬念」单独看**：一条永远不回收的悬念，会稀释所有伏笔的分量。  
> 读者被训练出"挖的坑不会填"预期后，对所有新钩子都会麻木。  
> `due` 会把它们单独标出来逼你决策：补章号，或确认废弃。

### 其他子命令

```bash
python $S/debt.py --project <书稿根> status           # 全部债务，按紧迫度排序
python $S/debt.py --project <书稿根> reveal           # 真相揭示节奏体检
python $S/debt.py --project <书稿根> due --json       # 机器可读
```

`reveal` 专查一件事：**待揭示真相积压**。  
真相埋太久不揭示，读者会放弃等待——这条比伏笔更容易被忽略，  
因为作者总觉得"读者应该记得住"。实际留存数据显示，第 30 章后仍未揭示的核心真相，  
读者的追问意愿已经衰减到不足以支撑追读。

## 四、recall.py：派生检索

### 三种索引来源

`index` 会把三类内容摊平成可检索片段：

| 来源   | kind                                                                                     | 典型片段               |
| ---- | ---------------------------------------------------------------------------------------- | ------------------ |
| 追踪台账 | `character` `foreshadow` `timeline` `constraint` `risk` `commitment` `position` `recent` | 角色卡、伏笔、真相、下章承诺     |
| 正文   | `chapter`                                                                                | 按场景切段（默认 1800 字一段） |
| —    | —                                                                                        | —                  |

### 检索模式

| 模式       | 触发条件                          | 说明                        |
| -------- | ----------------------------- | ------------------------- |
| `bm25`   | 默认，零配置                        | 中文按单字 + bigram 切分，拉丁按词。够用 |
| `hybrid` | 书稿根有 `.env` 且配了 `EMBED_*` 三元组 | BM25 + 向量余弦，权重 0.6        |

### 检索链路：三层

```
BM25 粗排  →  向量精排  →  rerank 定稿
（默认）      （配 EMBED_*）（配 RERANK_*）
```

**为什么要 rerank**：向量余弦只能算语义相似度，区分不出"提到了但不重要"和
"这才是主角要的"。rerank 是真正决定排名的最后一关。

### 智谱配置（推荐）

**端点**：`https://open.bigmodel.cn/api/paas/v4`
**key**：https://bigmodel.cn/usercenter/apikeys

在**书稿根目录**放 `.env`（或复制 `templates/env.example.zhipu`）：

```
EMBED_BASE_URL=https://open.bigmodel.cn/api/paas/v4
EMBED_MODEL=embedding-3
EMBED_API_KEY=你的key
EMBED_DIM=1024
RERANK_BASE_URL=https://open.bigmodel.cn/api/paas/v4
RERANK_MODEL=rerank
```

然后重建索引：

```bash
python $S/recall.py --project <书稿根> index
python $S/recall.py --project <书稿根> status   # 确认模式是 hybrid
```

#### 配置项全表

| 变量 | 必填 | 说明 |
|---|---|---|
| `EMBED_BASE_URL` | ✅ | 智谱固定 `https://open.bigmodel.cn/api/paas/v4` |
| `EMBED_MODEL` | ✅ | `embedding-3`（推荐）/ `embedding-2` |
| `EMBED_API_KEY` | ✅ | 智谱 API Key |
| `EMBED_DIM` | ❌ | 256/512/1024/2048。**长篇推荐 1024**——精度够用、体积减半 |
| `EMBED_MAX_CHARS` | ❌ | 单条送入上限，默认 1800 字符 |
| `RERANK_BASE_URL` | ❌ | 同 EMBED_BASE_URL |
| `RERANK_MODEL` | ❌ | `rerank` |
| `RERANK_API_KEY` | ❌ | 留空则复用 `EMBED_API_KEY` |
| `RERANK_MAX_DOCS` | ❌ | 候选池上限，默认 50 |

> ⚠️ **`.env` 的位置很重要**：本实现同时读取「书稿根的 .env」和「当前工作目录的 .env」，
> **书稿根优先**。早期版本只读当前工作目录，导致 `--project` 指向别处时配置静默失效、
> 永远降级到 BM25 且无任何提示。若配置了却仍是 bm25 模式，先跑 `status` 看提示。

#### 智谱两个必须知道的限制

**① embedding-3 单条上限 3072 token（中文约 2000 字），超出会静默截断且不报错。**
表现是"检索不到片段末尾的信息"，非常难查。本实现默认截断 1800 字符留足余量，
需要调整就用 `EMBED_MAX_CHARS`。

**② rerank 的 `top_n` 是"你要几条"，不是"候选池大小"。**
`documents` 列表才是候选池。`top_n` 设成比候选数还大不会报错，但也没有精排效果，白花钱。

#### 成本

| 项目 | 单价 | 600 章实际开销 |
|---|---|---|
| embedding-3 | 0.5 元/百万 token | 建索引约 0.45 元（一次性） |
| rerank | 0.8 元/百万 token | 单章约 0.001 元 |

**全程写完 600 章约 1 元。** Batch API 能再打5 折，但建索引只做一次，不值得为它加复杂度。

> ⚠️ **数据出境**：配了 embedding 后，**小说正文会发到智谱服务器**。
> 不接受就保持 BM25（不配 `.env` 即是）。NSFW、涉密内容尤其注意。

#### 索引维度守卫

换了 `EMBED_MODEL` 或 `EMBED_DIM` 之后，旧索引与新查询维度对不上，
余弦会**静默算错**（表现为"向量层突然失效"而非报错）。本实现在 `_load_index` 加了守卫：

```
索引由 embedding-3 构建，当前配置是 embedding-2。请重建：
     python recall.py --project <书稿根> index
```

### 其他配置来源

BM25 是默认，零配置。若用别家 embedding 服务，只要兼容 OpenAI 的
`POST {base}/embeddings`（返回 `data[].embedding`）即可，模型名换 `EMBED_MODEL` 就行：

| 服务 | EMBED_MODEL 示例 | 说明 |
|---|---|---|
| 智谱 | `embedding-3` | 推荐，中文好、便宜 |
| ModelScope | `Qwen/Qwen3-Embedding-8B` | 免费额度，需 modelscope token |
| 阿里 DashScope | `text-embedding-v3` | |
| OpenAI 兼容中转 | 各自模型名 | 你的 token-hub 若支持 `/embeddings` 也可 |

注意部分 OpenAI 兼容中转**只代理 chat 不代理 embeddings**，需要实测确认。

### 章节号是精确定位符，优先级最高

查 `第21章` 时，`第 9 章 / 第 284 章 / 第 542 章` 在纯 BM25 下得分几乎相同
（33.89 / 33.69 / 33.65）——因为 600 章里相同的人名、物品、地点满地都是，
而"21"这个真正的定位信息被当普通词丢掉了。

本实现把 `第N章` / `chN` / `chapter N` 抽成独立维度，命中时**压倒性置顶**（+1000 分）；
片段正文里明确提到该章的次级加权（+100）。600 章实测：

```
查询 "第21章 亲子鉴定 顾长风"
  [1] 伏笔 F013（埋于第21章）        1038 分
  [2] 第21章 · 第1段（正文原文）     1018 分   ← 修前进不了 top5
  [3] 第9章 / 第284章 ...33 分                ← 噪音被压到 1000 分以下
```

**长篇里"回到某章去看原文"是最常用操作，这条不能失效。**

想升级时在书稿根放 `.env`：

```
EMBED_BASE_URL=https://api-inference.modelscope.cn/v1
EMBED_MODEL=Qwen/Qwen3-Embedding-8B
EMBED_API_KEY=你的key
```

然后 `python $S/recall.py --project <书稿根> index` 重建。  
**注意**：配了向量层后，小说正文会发到该embedding 端点。  
介意就保持 BM25。

### 按类型过滤

写某类内容时只看相关类型，噪声更低：

```bash
# 写新角色出场前
python $S/recall.py --project <书稿根> query "新角色名" --kind character --kind timeline

# 回收伏笔前
python $S/recall.py --project <书稿根> query "F001 那封信" --kind foreshadow --kind chapter

# 推进主线前，只看真相
python $S/recall.py --project <书稿根> query "转让协议" --kind timeline
```

## 五、什么时候跑、跑几次

| 时机           | 动作                                      |
| ------------ | --------------------------------------- |
| **每次动笔前**    | `debt.py due` + `recall.py query`（本章要素） |
| 台账 commit 之后 | `recall.py index` 重建索引                  |
| 连续写 3 章以上    | `debt.py reveal` 看真相积压                  |
| 每卷收尾         | `debt.py status` 全量过一遍，决定哪些债留到下一卷       |
| 重写已提交章       | 先 `recall.py query`捞齐该章依赖的前文，再动笔        |

**写前必须把检索结果读进上下文**，不能只跑不读——跑完不读等于没跑。

## 六、150 万字规模实测（600 章模拟语料）

用 600 章 / 50 伏笔 / 30 真相 / 10 角色的合成语料实测，结论如下。

### 上下文预算：全文塞不进，也不该塞

| | token 量 | 占 32k 窗口 |
|---|---|---|
| 全文正文（约 18 万字符） | ~89,000 | **279%** —— 塞不下 |
| 单章写作实际需要（细纲+摘要+角色卡+债务提示+召回 top6） | ~5,600 | **17%** —— 健康 |

**这是整件事的关键**：单章写作不需要全文，需要的是"结构化状态 + 精准召回"。
所以决定成败的是**召回质量**，不是索引规模或能不能全文加载。

### 有了 1M 上下文之后呢？（`scripts/bench_context_cost.py`）

GLM-5.3 / GLM-5.3-Flash 都有 **1M 上下文**，这让"全书塞进去"从不可能变成可能。
但成本上完全不成比例。150 万字 / 600 章实测测算：

**装不装得下**

| 换算率 | 全书 token | 占 1M 窗口 | 结论 |
|---|---|---|---|
| 1字≈1.0 token | 1,500,000 | 150% | 超50% |
| 1字≈0.8 token | 1,200,000 | 120% | 超 20% |
| 1字≈0.6 token | 900,000 | 90% | 勉强装下 |

**付不付得起**

| 方案 | 全程 | 每章 | 每万字 |
|---|---|---|---|
| A 每章塞全书（缓存命中 2 元/百万） | **1,440 元** | 2.4 元 | 9.60 元 |
| A 每章塞全书（未命中 8 元/百万） | **5,760 元** | 9.6 元 | 38.40 元 |
| B 只送精准召回（Flash 5 折） | **4 元** | 0.006 元 | 0.03 元 |
| B 只送精准召回（旗舰） | **77 元** | 0.129 元 | 0.52 元 |

**相差 373 倍。** 关键在于：塞全书**不是付一次，是每写一章都重传一遍**，
全书越大翻账越贵——第 600 章时单章输入就是 120 万 token。

**所以 1M 上下文是检索层的补充，不是替代品：**
- 前半程全书塞得下，可以先不搭检索，省掉前期功夫
- 临界点约 **500 章**（单章 2,000 token × 500 ≈ 1M），超过就必须切召回
- 你的目标 600 章超出临界点 100 章，**检索层是必需品**

复跑：`python scripts/bench_context_cost.py --chars 3000000 --chapters 1200`

### 性能

| 操作 | 耗时 |
|---|---|
| 索引构建（717 个片段） | 0.61 秒 |
| 单次检索 | < 0.1 秒 |
| 债务计算（50 条） | < 0.05 秒 |

无性能顾虑，不需要常驻服务。

### 实测暴露的两个真bug（已修）

**① 章节号是精确定位符，但分词时丢掉了**

查"第 21 章 亲子鉴定 顾长风"时，第 9 章、第 284 章、第 542 章得分几乎完全相同
（33.89 / 33.69 / 33.65）——因为 600 章里"亲子鉴定""顾长风"满地都是，
而"21"这个真正的定位信息被当普通词丢在一边。

修法：抽出 `第N章 / chN / chapter N` 为独立高维维度，命中时压倒性置顶（+1000 分）。
修后同一查询，第 21 章正文从"进不了 top5"变成"稳居第 2"（1018 分 vs 噪音 33 分）。

**② 债务紧迫度封顶导致长篇排序失效**

见第三节。50 条债全部并列满分时，"按紧迫度排序"等于没排序。

### BM25 到底够不够？一组对照实测（`scripts/bench_bm25.py`）

这是决定"要不要配 embedding key"的唯一依据。跑两组配对查询：

- **词面组**：查询词直接抄自答案 → BM25 的能力上限
- **改写组**：查询是场景描述，答案用完全不同的措辞，且**零实词重叠**（脚本自检，不通过直接退出）

600 章 / 600 片段 / top-6 实测：

| 组别 | 命中率 | 明细 |
|---|---|---|
| 词面组（抄答案） | **5/5 = 100%** | 全部第 1 位 |
| 改写组（零重叠） | **2/5 = 40%** | 中 1 条漏检、命中的第 1 /第 3 位 |
| 章节号定位 | **3/3 = 100%** | 全部第 1 位（+1000 置顶生效） |

复跑：`python scripts/bench_bm25.py --ch 900`

**判读**：章节号定位和词面检索 BM25 已经满分，缺口**只出现在"换个说法问"**这件事上。
缺口约 60%，正是向量层要补的部分。所以：

- 你习惯**用原词/专名/章节号检索** → 只用 BM25，**不要配 key**，省下全部成本和故障面
- 你习惯**用描述句检索**（"上次那个替他挡刀的人后来怎么了"）→ 缺口明显，值得开向量层

### 评估检索的三个坑（都踩过，别重犯）

1. **别把查询抄进答案**。第一版实验把查询串原样写进 payload，
   recall@6 得到假性 100%。现在脚本有自检，零实词重叠不通过就退出。
2. **别用"删掉埋点看结果变不变"做证伪**。删掉后答案已不存在，
   结果当然不变，这个设计什么都证明不了。
3. **别用 top6 目视代替 recall@k**。合成语料本身无语义，
   top6 由片段长度和位置噪声决定，看起来"命中"其实没命中。

### 真实成本提醒

50 条伏笔 × 600 章，测出 `due` 会报出 **20+ 条高危债**。这不是工具的问题，
是长篇的真实代价——**每一卷（约 100 章）必须还掉 20 笔债，
即平均每 5 章就得兑现一条**。

如果你的规划是"埋 50 条、最后 3 卷一起收"，那从第 2 卷起`due` 就会一直报警。
**伏笔总量应该按"每卷可消化量"来控制**：100 章一卷，一卷最多新埋 15~20 条。
工具只能告诉你欠了多少，埋多少是创作决策。

## 七、与 webnovel-writer 的关系（为什么不直接装它）

本模块的检索与债务逻辑借鉴了[webnovel-writer](https://github.com/lingfengQAQ/webnovel-writer)（GPL-3.0）  
的设计思路，但实现刻意不同：

|      | webnovel-writer                                           | 本模块                       |
| ---- | --------------------------------------------------------- | ------------------------- |
| 状态真源 | `.story-system/` + `.webnovel/state.json` + `index.db` 多轨 | 单轨：`_tracking-state.json` |
| 索引载体 | SQLite（`index.db` / `vectors.db`）                         | 单个 JSON 缓存，可删可重建          |
| 缺失能力 | —                                                         | 无 embedding key 时BM25 兜底  |
| 迁移成本 | 需改15 个文件的 `CLAUDE_PLUGIN_ROOT`、重写 8 个 frontmatter         | 无                         |

**没装整套的理由**：它与novel-forge 的单一真源原则冲突——  
两个状态系统会互相覆盖。加上它的 hooks 依赖 Claude Code 的  
`SessionStart` / `PreToolUse` 机制，在本环境无法迁移。

**取其长处、避其双轨**，是更稳的路。GPL-3.0 的许可要求：  
若你直接复制了其源代码，此处需保留版权声明；若只借鉴设计思路（本文档情况），  
无强制义务，但已在文档中标注来源。

## 八、常见问题

**Q：`recall-cache` 该不该提交到git？**  
不该。它是派生产物，在 `.gitignore` 里加一行 `.recall-cache/`。  
丢了重跑 `index` 即可，结果完全一致。

**Q：索引和台账不一致怎么办？**  
以台账为准。`recall.py index` 会重新摊平台账。  
建议流程：先 `tracking_commit.py commit`，再 `recall.py index`，顺序不能反。

**Q：正文目录名不是 `正文/` 行不行？**  
可以。`recall.py` 依次扫描 `正文/`、`chapters/`、`text/`，  
文件名只要含数字就能识别章节号（第1章 / 第0001章-标题 / 001_标题 都行）。

**Q：为什么不用向量库？**  
长篇中文场景下bigram BM25 的性价比更高：零依赖、零延迟、零成本、可解释。  
如果你写到 500 章以上且检索明显不够用，再配 embedding。  
那时索引层会自动升级成 `hybrid`，脚本不用改。

## 九、台账 schema 兼容（两种写法都能跑）

台账字段名历史上出现过几种写法。早先脚本把字段名写死了，
换成另一种写法会**静默漏检**——不报错、不提示，只是永远检索不到 /
算不出债务，排查起来极其昂贵。现在两种写法都接受：

| 概念 | 标准写法（模板默认） | 也接受 |
|---|---|---|
| 当前章号 | `last_chapter` | `last_chapter_written` / `current_chapter` / `last_ch` |
| 伏笔列表 | `foreshadow` | `foreshadowing` |
| 伏笔埋设章 | `planted_chapter` | `planted_ch` |
| 计划回收章 | `planned_resolution_chapter` | `target_ch` / `due_chapter` |
| 伏笔摘要 | `summary` | `desc` / `content` |
| 角色 | `character_snapshots`（dict） | `characters`（list，带 `name`） |
| 长线约束 | `context.long_term_constraints` | 顶层 `constraints`（字符串或 `{"text":…}`） |
| 连贯性风险 | `context.continuity_risks` | 顶层 `risks` |
| 下章承诺 | `context.next_chapter_commitments` | 顶层 `commitments` |
| 近期摘要 | `context.recent_chapters` | 顶层 `recent` |

改 schema 后务必跑一遍回归测试：

```bash
python scripts/test_schema_compat.py
```

它用两套等价台账交叉验证召回 kind 分布、条目内容、债务紧迫度必须完全一致。
19 项全绿才算通过。

**约束类字段两种形态都支持**：字符串直接用，`{"text": "..."}` 会自动取出正文，
不会在检索结果里倒出 Python dict。
